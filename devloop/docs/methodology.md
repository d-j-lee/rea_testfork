# 작업 방법론

devloop의 스킬이 따르는 작업 방식이다. 사람이 Claude와 함께 일할 때도 같은 원칙을 따른다.
규칙의 세부(등급 상한, 린트 코드, 종료 게이트)는 [증거 규칙](../plugins/devloop/references/evidence.md)이 소유한다.

## 1. 하나의 척추, 네 개의 루프

```
Intake ─▶ Evidence ─▶ Analysis ─▶ Plan ─▶ Apply ─▶ Verify ─▶ Close ─▶ Retro
  사실 고정    증거 수집    가설·판별     합의      적용      red→green   게이트      지식 반영
```

| 루프 | 끝나는 조건 | 주 산출물 |
| --- | --- | --- |
| 설계검토 `design-review` | 질문이 모두 답 또는 보류, 교차검증 기록 | REQ, 발견사항(심각도·분류), 기획 질문, 서버 설계 제안, 검증 시드 |
| 기능검증 `verify` | 모든 REQ에 실행 결과 또는 이유 있는 SKIP, TODO 0 | REQ×CHK 매트릭스, 시나리오(회귀 자산), 버그 케이스 |
| 조사 `investigate` | 원인(등급 명시), 영향 범위, 대응안, 사람 결정 | 타임라인(UTC), 가설표, 재현, 영향 조회 |
| 수정 `fix` | 같은 재현의 FAIL→PASS, 교차검증 | 최소+관련 정리 수정, 회귀 CHK, PR 본문 |

루프는 서로 이어진다. 설계검토의 검증 시드는 verify로, verify의 FAIL은 bug 케이스로, 조사의 결론은 fix로, 종료된 케이스는 retro로 넘어간다.

## 2. 증거로 말한다

- **확인 · 도출 · 추론 · 미확인**을 구분한다. 결론은 가장 약한 근거의 등급을 넘지 못한다.
- 원인·효과 판정은 재현이나 전후 대조가 있을 때만 도출이다. 코드를 읽고 "그럴 것"이라고 판단한 것은 추론이다.
- 사람·티켓·문서·다른 에이전트의 말은 "그렇게 적혀 있다"까지만 확인이다.
- "없음·통과·정상"은 본 범위(환경·빌드·기간·표본) 안에서만 말한다. 잘린 결과를 전체로 쓰지 않는다.
- 도구 출력은 `--save`로 원장에 남긴다. 원장은 고칠 수 없고, 정정은 새 항목으로 대체(`--supersedes`)한다.

## 3. 사람과 합의하는 지점

Claude는 다음에서 멈추고 묻는다. 질문과 결정은 `case ask` / `case decide`로 원장에 남는다.

| 지점 | 예 |
| --- | --- |
| 되돌리기 어려운 작업 | 라이브 데이터 보정, 배포, 설정 변경, 보상 지급·회수 |
| 범위가 바뀌는 판단 | 버그로 보이던 것이 기획 의도일 수 있음, 수정이 다른 시스템을 건드림 |
| 사람만 답할 수 있는 입력 | 기획 의도, 보상 정책, 운영 일정, 환경 접근 권한 |

데이터 보정은 Claude가 스크립트, dry-run 집계, 롤백 계획을 **작성**하고 사람이 **실행**한다.

## 4. 독립 교차검증

결론·설계·수정을 확정하기 전에 `adversary` 에이전트가 반박을 시도한다. 확인하는 것은 다음과 같다.
- 결론이 거짓이어도 같은 증거가 나올 수 있는가?
- 대안 설명을 배제했는가?
- 범위 밖으로 일반화했는가?
- 같은 패턴의 다른 호출부가 있는가?

결과는 review 증거로 남고, 종료 게이트가 이 기록을 요구한다.

## 5. 가볍게 시작하고 필요할 때 기록한다

몇 번의 확인으로 끝나는 질문은 케이스 없이 답한다. 출처는 문장 속에 둔다. 다음 중 하나라도 해당하면 케이스를 만든다.
- 세션을 넘긴다.
- 증거를 보존해야 한다.
- 수정이나 데이터 대응이 걸린다.

케이스는 기본적으로 로컬에만 둔다. 개인정보가 들어갈 수 있어서다. 공유는 `report`로 정제한 글로 한다.

## 6. 자가 진화

- `retro`는 종료 케이스에서 교훈을 뽑아 팀 지식에 반영하는 변경안을 만들고, 반영은 승인 후에 한다. 반영 대상은 체크리스트, 함정, 시스템 지도, 시나리오다.
- 같은 내용은 합치고 근거 케이스를 남긴다. 덧붙이기만 해서 누더기가 되지 않게 한다.
- `case stats`의 강제 종료율과 종료 시간은 프로세스가 현실과 어긋나는 신호다. 게이트를 고칠지, 습관을 고칠지 논의한다.
- 플러그인 자체는 `evals/`로 회귀를 측정한다(`claude plugin eval`). 스킬 문구를 바꿀 때는 전후 점수를 비교한다.

## 7. 비용 감각

- 컨텍스트는 아낀다. 로그는 원문 대신 템플릿·타임라인으로 보고, 큰 분석은 `log-analyst`에 맡겨 결론만 받는다. 출력에는 항상 전체 건수와 반환 건수를 함께 둔다.
- 플러그인이 항상 차지하는 컨텍스트는 약 1,200 토큰이다(`claude plugin details`, 0.1.0 측정). 수동 스킬(setup·report·retro)은 자동 호출 목록에 넣지 않았다.
