# devloop 아키텍처

게임 서버 컨텐츠 개발의 설계검토 → 기능검증 → 버그/이슈 조사 → 대응 → 회귀검증을 Claude Code와 함께 "완결될 때까지" 굴리기 위한 구조.

## 1. 문제 정의

| 현업 비용 | 원인 | devloop가 겨냥하는 것 |
| --- | --- | --- |
| 설계검토가 개인 경험에 의존하고 누락이 늦게 발견된다 | 관점이 암묵지이고, 기획서↔코드↔DB↔데이터 테이블 대조를 손으로 한다 | 리스크 체크리스트 + REQ 추출 + 코드·테이블 대조를 한 흐름으로 묶는다(`design-review`, `doc text`, `code-tracer`) |
| 검증이 "해본 것"으로 끝난다 | REQ와 테스트 사이의 추적성이 없다 | REQ×CHK 매트릭스. 미커버 REQ와 실행 증거 없는 PASS를 기계적으로 검출한다 |
| 로그·DB를 눈으로 훑는다 | 로그가 크고, 서버가 여럿이고, 시간대·인코딩이 섞여 있다 | 템플릿 요약, 레벨 인식 전후 비교, 키 기반 타임라인(Δms, 편차 경고), 증거 자동 기록 |
| AI 결론을 얼마나 믿을지 모른다 | 확인한 것과 추론한 것이 섞인다 | 출처에 따른 등급 상한, 부풀림 린트, 원인 판정에 재현 요구 |
| 봇테스트 구축과 작성 비용이 크다 | 시나리오 작성·실행·판정이 모두 코드 작업이다 | 선언형 시나리오(병렬·반복 분포), 기존 봇을 감싸는 JSON-lines 어댑터 |
| 세션이 끊기면 맥락을 잃는다 | 조사 상태가 대화 안에만 있다 | 케이스 파일과 원장, 세션 시작 시 열린 케이스 요약 |
| 운영 환경에 위험한 명령이 나갈 수 있다 | 환경 구분을 사람이 기억에 의존한다 | 티어 정책 가드(deny/ask), 읽기전용 정식 경로(`db query`) |

## 2. 구성과 의존 방향

```
┌────────────────── Claude Code ──────────────────┐
│ skills: 판단·순서·합의 지점   agents: 격리·교차검증    │ ← references/(플러그인 기본 지식) + .devloop/knowledge/(팀 지식)
│ hooks: PreToolUse 가드 · SessionStart 요약          │
└───────────────────────┬─────────────────────────┘
                        │ Bash: "<plugin>/scripts/devloop" …  (compact text / --json)
               ┌────────▼────────┐
               │  devloop CLI    │ case·ev · log · sql · db · bot · doc · hook   (stdlib Python ≥ 3.11)
               └────────┬────────┘
                        │ 워크스페이스 설정(.devloop/config.toml)과 어댑터를 통해서만
     ┌──────────────────┼───────────────┬────────────────┐
  로그 파일/명령 원천   DB 클라이언트(argv)   팀 봇(JSONL/python)   (선택) 다른 MCP: Jira·Slack·REA
```

- **안쪽은 바깥을 모른다.** 회사마다 다른 것은 워크스페이스 설정과 어댑터가 소유한다. 로그 포맷, DB 접속, 봇 프로토콜, 환경 마커가 여기에 해당한다. 플러그인은 기본값과 샌드박스만 가진다.
- **결정적인 일은 CLI가, 판단은 모델이 맡는다.** 파싱·분류·실행·검사는 코드로 하고, 가설·설계·글은 스킬과 에이전트가 한다.
- **해석은 한 곳에서 한다.** SQL 해석은 `sqlguard`, 인코딩은 `textio`, 시각은 `timeutil`, 등급 상한은 `ledger`, case.md 문법은 `case`가 소유한다. 가드·DB·봇은 이 소유자의 결과만 쓴다.
- **표준 라이브러리만 쓴다.** 사내 PC·서버(Windows 포함)에서 pip 없이 동작해야 하기 때문이다. 런처(`scripts/devloop`, bash)가 인터프리터 차이를 흡수한다.
- 최상위 `bin/`을 두지 않는다. claude.ai/Cowork는 `bin/`이 있는 플러그인을 설치하지 않으므로, 스킬 본문의 `${CLAUDE_PLUGIN_ROOT}/scripts/devloop`로 호출한다.

## 3. 데이터 모델

```
<workspace>/.devloop/
  config.toml        환경 티어·마커, 로그 프로필/원천, DB 명령, 봇 어댑터 (커밋)
  knowledge/         systems.md(도메인 지도) · checklist.md · pitfalls.md (커밋, retro가 갱신)
  scenarios/         봇 시나리오 = 회귀 자산 (커밋)
  cases/<ID>/        로컬 전용(.gitignore)
    case.md          서술의 단일 소유자 (front matter + 정해진 문법)
    ledger.jsonl     증거·질문·답·결정·상태·종료 이벤트의 단일 소유자 (CLI만 append: 파일 잠금 + 이전 줄 해시 체인)
    artifacts/       도구 출력·실행 로그·첨부 (해시 기록)
```

- 상태는 원장 이벤트로 기록하고, front matter의 `status`는 CLI가 갱신하는 사본이다. 둘이 다르면 린트가 오류를 낸다. 손으로 고친 흔적은 드러난다.
- 원장은 파일 잠금 아래에서 ID를 붙이며 추가한다. 동시 저장에도 E번호가 겹치지 않는다. 각 줄은 이전 줄의 해시를 담고, 아티팩트는 해시와 함께 기록된다. CLI 밖에서 생긴 변경은 `case check`가 오류로 보고한다.
- 파서는 문서화된 문법만 읽는다. 등급 태그, `[E#]`, `[REQ-#]`, 첫 헤더가 `CHK`인 표가 그것이다. 읽지 못한 "주장처럼 보이는" 줄과 CHK 행은 경고로 보고한다. 조용히 무시하지 않는다.

## 4. 증거 등급의 기계적 강제

- **상한은 출처가 정한다.** 해시로 남는 것은 확인이 될 수 있다(도구 출력, 실행, 파일 라인 스냅샷, 첨부). 재확인할 수 없는 메모는 추론이 상한이다. 보고·리뷰는 인용할 때 추론으로 계산한다. derived는 전제 중 가장 약한 등급을 넘지 못한다.
- **원인·효과**는 관찰이 아니다. 따라서 확인이 될 수 없고, 도출이 되려면 run/bot 재현 증거를 인용해야 한다.
- **종료 게이트**는 사유마다 다르다(fixed, data-fix, external…). fixed는 같은 회귀 CHK에서 FAIL 실행이 PASS 실행보다 먼저 있어야 한다. `--force`는 원장에 남고 `stats`의 강제 종료율로 드러난다.
- 이 장치들은 모델의 정직함을 대체하지 않는다. 정직한 경로를 싸게 만들고, 부정직한 경로를 눈에 띄게 만드는 것이 목적이다.

## 5. 안전 모델

1. **티어 판정.** 마커는 *데이터 플레인 명령*(DB·캐시 클라이언트, 쓰기 HTTP, 원격 실행)에서만 본다. 그래서 `grep live-01 app.log` 같은 일상 명령은 조용하다. 따옴표 안의 명령줄(`ssh host "mysql -e …"`, `bash -c "…"`)은 재귀로 분석하고 바깥 티어를 물려받는다.
2. **결정은 deny/ask만.** 가드는 allow를 내지 않는다. 사용자 권한 체계를 넓히지 않기 위해서다. 다음 경우도 ask로 실패한다.
   - 설정 오류, 예외
   - Python을 찾지 못함. 이때는 bash 런처가 직접 JSON을 낸다.
3. **CLI가 스스로 강제한다.** 가드를 거치지 않는 경로도 같은 정책을 적용받는다.
   - `db query`: 쓰기 거부, stage/live 결과 상한, 마스킹, SQLite는 `mode=ro` + `query_only`.
   - `bot run`: 시나리오 `allowed_tiers`와 티어 정책을 둘 다 통과해야 한다.
4. **분류기는 보안 경계가 아니다.** 실제 경계는 읽기전용 계정과 복제본이다. 데이터 보정은 사람이 실행한다.
5. **비밀값은 `${ENV}`로만 참조한다.** 원장에는 치환 전 템플릿만 남는다. 마스킹은 명시한 필드와 컬럼에만 한다. 이름 패턴으로 비밀을 추측하지 않는다.

## 6. 봇 시나리오

- 러너는 순서, 병렬(배리어), 반복, 단언, 프로브, 기록을 소유한다. 어댑터는 프로토콜을 소유한다.
- 배리어가 맞추는 것은 **클라이언트 송신 시점**뿐이다. 그래서 경합 검사는 `repeat`로 분포를 남기고, 출력에 송신 편차(spread)를 보고한다.
- `process` 어댑터는 요청 ID로 다중화한다. 기존 봇이 요청을 동시에 처리하기만 하면 언어와 무관하게 실제 동시성을 재현한다.
- 실시간 UDP 게임플레이는 범위 밖이다. 요청/응답형 컨텐츠가 대상이다.

## 7. 성능과 비용 (0.1.0 실측, Linux x64, Python 3.13)

| 항목 | 값 | 조건 |
| --- | --- | --- |
| 플러그인 상시 컨텍스트 | ~1,200 토큰 | `claude plugin details` 추정치 |
| `log scan` | 16.2초, 최대 RSS 22MB | 1,000,000줄 / 103MB, 정규식 프로필 |
| `log query --where uid=` | 10.6초, 22MB | 같은 파일 (`--key`는 7.8초: key=value 해석 생략) |
| `log timeline --where` | 10.0초, 22MB | 같은 파일 |
| 샌드박스 사건 전체 scan | 0.37초 | 8,144줄, 3개 소스 (gzip·CP949 포함) |
| PreToolUse 훅 | 중앙값 66ms, p90 77ms | n=20, bash 런처 경유. 훅 경로는 가드에 필요한 모듈만 import |

메모리는 스트리밍이라 입력 크기와 무관하다. 다만 timeline은 매치 레코드를 최대 10만 건까지 보관한다. GB 단위 로그는 `--since/--until`이나 원천 명령에서 먼저 좁힌다.

## 8. 범위 밖 (의도적)

- 회사 고유 시스템 구현(실제 봇 클라이언트, 로그 수집기 API): 어댑터와 설정으로 연결한다.
- 라이브 쓰기 자동화: 사람이 실행한다.
- 이슈 트래커·메신저: Claude Code의 커넥터(MCP)를 그대로 쓴다.
- 잠재 기능 시드: [decisions.md](decisions.md)의 "보류(시드)" 항목.
