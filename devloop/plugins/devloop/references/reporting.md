# 사람에게 보내는 글

케이스는 작업 기록이고, 보고는 읽는 사람의 결정을 돕는 글이다. 케이스를 그대로 붙여 넣지 않는다.

## 공통 원칙
- **결론 먼저, 한 문단.** 무엇이 문제였고, 지금 상태는 무엇이며, 상대에게 필요한 결정/행동은 무엇인지.
- 확실성은 문장으로 드러낸다: "재현으로 확인했습니다" / "로그상 일치하지만 재현 전입니다(추정)" / "확인하지 못했습니다(방법: …)". 등급 라벨을 나열하지 않는다.
- 수치에는 범위와 조건: "10/19 12:00~10/20 18:00 UTC, game-01·02 기준 42건". 잘린 결과는 잘렸다고 쓴다.
- 개인정보(계정·SteamID·IP)는 필요한 최소만, 외부 공유본에서는 가린다.
- AI 투의 군더더기(과한 서두, 반복 요약, 이모지, "도움이 되었길 바랍니다")를 뺀다. 팀 메신저/티켓의 평소 문체에 맞춘다.

## 독자별 틀
| 독자 | 담을 것 | 뺄 것 |
| --- | --- | --- |
| 기획 (설계검토 회신) | 확인 필요 질문(번호, 선택지와 각 결과), 명세 공백, 리스크 높은 순 3~5개, 서버 제안 요지 | 코드 세부 |
| QA (검증 결과) | REQ별 결과표(PASS/FAIL/SKIP+이유), 결함 링크, 재현 절차, 미검증 범위, 테스트 빌드·환경 | 내부 추론 과정 |
| 운영·CS (이슈) | 영향(누가·언제·얼마나), 현재 조치, 사용자 안내 문구 초안, 보상/회수 결정 필요 사항 | 원인 코드 상세 |
| 개발 (PR·포스트모템) | 근본 원인(재현 근거), 수정 방식과 대안, 회귀 테스트, 남은 리스크·정리 과제 | 고객 응대 문구 |

## 포스트모템 골격
요약 → 영향 → 타임라인(UTC) → 근본 원인(+트리거와 결함 구분) → 감지·대응에서 잘된 점/아쉬운 점 → 재발 방지(담당·기한) → 부록(증거 목록).
